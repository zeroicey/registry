① 系统概览

一句话把系统说清楚。

这是一个人人员信息登记系统
核心对象是 users（登记对象 = 人员）。字段不是写死的，而是通过 attributes（可动态增删的「自定义收集字段」元数据，类似表单设计器）来定义， 因此字段的值必须动态存储。另有 comments（备注）和 attachments（材料附件）挂在 user 之下。

系统全景（概念级）

为什么要把「字段」做成表？
因为这是登记系统：不同项目/批次要收集的字段不一样，而且会随时加字段。把字段写成固定列就锁死了扩展性。 于是「字段定义」进 attributes 表，「字段的值」单独存——这是整套设计的核心。

③ 旧版设计的 6 个问题

① 值用属性 ID 做 key
{"1":"男","2":25} 不可自解释，排查和跨环境导入都要反查 attributes； 属性改名要 rewrite 全部用户数据；attributes.key 存在却从未被值使用。
② 软删除设计硬伤
is_delete + key UNIQUE：属性软删后，同 key 永远无法重建； 无 deleted_at；所有查询都要手动过滤 is_delete。
③ 类型与校验只在应用层
JSONB 存任意类型，仅靠 Java 的 ProfileValidationService 手写 switch 校验，绕过即脏数据； 只有 string/number/bool 三种，表达不了 date、select；无任何规则表达（required、min/max、regex、选项、默认值、排序分组）。
④ 并发与留痕缺失
同一字段并发写是 last-write-wins；没有任何变更历史——不知道谁、何时、把哪个字段从什么改成了什么。
⑤ 查询能力弱
JSONB 的 GIN 索引只能做包含查询（@>），无法按字段值范围/排序筛选 ——比如「筛出 age>30 的人」做不到。用户列表也无分页。
⑥ 风格不统一 + 缺失字段
status 用 VARCHAR+CHECK 而 type 用枚举；object_key 无唯一约束、md5 无索引； comments 无 created_by；users 只有 real_name、无唯一业务编号，重名无法区分。

④ 新版设计（TS / Drizzle，6 张表）

针对上面 6 个问题逐一回应：值规范化、软删重做、类型扩展、历史留痕、查询可索引、字段补齐。

对比框：同一份业务数据，两种存法

旧版 = 一个 JSON blob
users.profiles = {"1":"男","2":25}
· key 是属性 ID
· 无校验规则、无历史、无法按字段查询
新版 = 多行 + 历史
attribute_values → (gender,"男")、(age,25)
attribute_value_history → age 24→25 留痕
· key 是业务 key、可索引、可留痕、有规则
注意：API 形状不变
对前端而言，接口仍是 PATCH /users/:id/profile，请求体还是 {"gender":"男","age":25}。 变的只是内部实现：key 从「属性 ID」换成「业务 key」；DB 从「一个大 JSON」换成「多行 + 历史」。 这样迁移改造对调用方是透明的。 
// 请求不变，只是 key 从 ID 变成业务 key
PATCH /users/1/profile
{ "gender": "男", "age": 25 }

⑤ 数据流（新版）

写、读两个核心流程，配套 Hono 路由说明。

写 写入流程 PATCH /users/:id/profile

// Hono 路由 · zod = buildValidator(attributes, config)
app.patch('/users/:id/profile', async (c) => {
  // 1. 按 attributes.config 动态生成 Zod 校验器
  const schema = buildDynamicZod(attrs);       // required/min/max/regex/options…
  const cleared = schema.parse(body);             // 2. 校验类型 + 规则（失败即 400）

  return db.transaction(async (tx) => {
    // 3. 批量 upsert 值表
    for (const [key, val] of Object.entries(cleared)) {
       await tx.insert(attribute_values)
         .values({ userId, attributeId: keyMap[key], value: val })
         .onConflictDoUpdate({ /* ON CONFLICT (user_id,attribute_id) DO UPDATE */ });
    }
    // 4. 同一事务内记录 old/new
    await writeHistory(tx, diffs);               // attribute_value_history
    return buildProfile(c);                      // 返回最新 profile
  });
});

读 读取流程 GET /users/:id

// 读取：把值表多行聚合回一个 profile 对象
select u.id, u.real_name, jsonb_object_agg(a.key, av.value) AS profile
from users u
join attribute_values av on av.user_id = u.id
join attributes a        on a.id = av.attribute_id
where u.id = :id
group by u.id

⑥ 新旧对比表 + 取舍点

维度对比

维度旧版新版
值存储profiles JSONB 大 blobattribute_values 规范化表（一行一字段）
字段 key属性自增 ID（`{"1":…}`）业务 key（`{"gender":…}`）
软删除is_delete + key UNIQUE（软删后无法重建）deleted_at + 部分唯一索引 UNIQUE(key) WHERE deleted_at IS NULL
类型3 种枚举（string/number/bool）5 种（+date/select）+ config 规则
并发与历史无 · last-write-winsupsert + attribute_value_history 留痕
按字段筛选做不到（GIN 只支持包含查询）可走 attribute_id 索引
数据自解释性差（需反查 attributes）好（业务 key 即含义）
表数量4 张6 张（+attribute_values +attribute_value_history）

4 个取舍点

① 类型扩到 5 种
新增 date、select。select 的下拉选项放 config.options， 不必为每种 UI 控件单独建表，靠 config 一个字段覆盖各类表达。
② 校验规则放 config JSONB + Zod 动态生成
required/sort_order/group/options/min/max/regex/default/help 统一进 config； 运行时用 Zod 按 config 动态构造校验 schema，校验逻辑集中在数据层而非散落手写。
③ users.code 业务编号
为每个用户分配唯一业务编号（P001…），配合 UNIQUE 约束，彻底解决「重名人员无法区分」， 也是外部导入/去重的稳定锚点。
④ 彻底删除 users.profiles
attribute_values 成为唯一真相源（single source of truth）。避免「profiles 与 values 双写不一致」的坑， 未来加字段/改规则都只动一张表。
取舍总结
新版用「多两张表 + 规范化」换来：可自解释、可软删重建、可校验、可留痕、可就地查询。 代价是读路径需要一次 join 聚合——已在流程⑤里给出 jsonb_object_agg 的化解方案，且对 API 调用方透明。
